# 数据利用率与读取必要性分析

## 1. 每 token 读什么

| 数据 | 大小/token | 利用率 | 是否必要 |
|---|---|---|---|
| 专家（routed, top-6） | 6 x 18.8 MB = 113 MB/层 | **100%**（用到的专家权重全矩阵参与计算） | 必要 |
| 专家（未路由） | 378/384 专家 **不读** | 0% | 不读（MoE 稀疏 = 1.6% 激活） |
| 常驻层权重 | 7 层 x 190 MB（一次性） | 100% | 必要 |
| 流式层权重 | 33 层 x 190 MB（每 token H2D） | 100%（整层参与） | 必要 |
| Engram 表 | 用到的行（行级读） | 行 100% | 必要（未用行不读） |
| KV / 压缩 KV | 窗口 128 + 压缩位置 | 100% | 必要 |

**结论**：按 token 计算，**读到的数据 100% 参与计算**（专家是稀疏激活，未激活专家根本不读）。
不存在"读了不用"的浪费——浪费只可能在：
1. **重复读**（命中率 < 100% 时同专家被多次读）→ 缓存/预取解决
2. **读得慢**（磁盘并发不足）→ 本次改 16 并发
3. **量化更小**（fp4 已是 4bit，专家权重 18.8MB 是 4bit packed + scale，理论下限）

## 2. 每个 token 的专家 I/O 下界

- top-6 x 18.8 MB x 40 层 = **4.5 GB/token（若全 miss）**
- 命中率 h 时：4.5 x (1-h) GB/token
- 磁盘 11.9 GB/s → **全 miss 时 0.38 s/token 是 IO 下界**（=2.6 tok/s 上限）
- 命中 90% 时：0.45 GB/token → 0.038 s/token（IO 不再是瓶颈）

## 3. 当前实测（26 层，冷启动单 token）

- fetch 磁盘读 4.9 GB/s（6 并发，**磁盘 42%**）→ 改 16 并发后目标 8-11 GB/s
- 命中 42%（冷）→ 稳态（相邻 token 路由相似）应 90%+
- fetch 23 ms/层（6 专家 113MB @4.9GB/s），H2D 4 ms/层，锁/其他 ~10 ms/层

## 4. 读取带宽上限（实测，Windows）

| 方式 | 线程 | 实测 | 说明 |
|---|---|---:|---|
| buffered（file.readinto） | 2/4/6/8/12/16 | 4.36/5.13/**5.28**/5.14/4.33/5.27 GB/s | **平台上限 ~5.3GB/s**（OS page cache 双拷贝 + 单文件锁） |
| direct（FILE_FLAG_NO_BUFFERING + scratch） | 6-8 | 3.75 GB/s | scratch 双拷贝更慢 |
| 理论（PCIe5.0 x4） | - | 11.9 GB/s | **需要 OVERLAPPED 异步 IO**（ctypes，未实现） |

**结论**：当前读路径在 buffered IO 下已到上限（5.3GB/s，磁盘 45%）。要接近 11.9GB/s 只能实现 Windows OVERLAPPED 异步读（单文件多 outstanding IO），这是下一步。

## 5. 优化优先级（按利用率）

1. **读并发 16**（打满磁盘队列）——已改
2. **命中率**（缓存 14GB + 预测）——稳态 90%+
3. **H2D 与计算重叠**（双缓冲，待修复后启用）
4. **GPU kernel**（MoE fp4 融合、attention 全融合、CUDA graph）——GPU 时间本身 2.2s/token
